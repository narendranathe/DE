Recursive CTE (hierarchy)

WITH RECURSIVE hierarchy AS (
 SELECT id, manager_id, 1 AS depth FROM employees WHERE id = ?
 UNION ALL
 SELECT e.id, e.manager_id, h.depth + 1 FROM employees e JOIN hierarchy h ON e.id = h.manager_id

Joins: INNER (matches only) · LEFT (all left + NULLs) · FULL OUTER · CROSS (date-spine fills) · Anti-join NOT EXISTS / LEFT JOIN ... WHERE r.id IS NULL (the orphan-detection pattern).

Plan operators: Nested Loop (small outer + indexed inner) · Hash Join (large, no index) · Merge Join (both sorted on key) · Index Seek (good) vs Scan (bad unless tiny).

Indexing: clustered = narrow + ever-increasing; non-clustered with INCLUDE for covering; WHERE/JOIN cols first; filtered indexes for skewed predicates.

04 HLD Concepts +

Scale axes: throughput (RPS) · latency (p50/p99/p999) · storage (GB/day) · durability (RPO) & availability (RTO, SLO 9s) · consistency model.

Consistency: CAP (under partition choose C or A); PACELC (else: latency vs consistency). Linearizable > sequential > causal > eventual. SI allows write-skew; serializable doesn't.

The Type System

0 / 150 XP
CUTOFF TARGET
mypy --strict sentinel/models.py passes with 0 errors, and you can defend TypedDict vs Protocol vs plain annotation out loud.
01CONCEPT

Type hints + a static checker (mypy) let a team catch shape/contract bugs before runtime — the Python equivalent of column types + constraints on a SQL table. Engineers reach for this constantly because untyped Python rots fast on a team: nobody knows what a function actually accepts. On data/AI-infra teams, mypy --strict in CI is table stakes, and typed code is the difference between junior- and senior-looking Python.

02ALTERNATIVES
  • TypedDict — when data travels as a dict (JSON, row records). Lightweight, no class needed.
  • Protocol — when you care what an object can do, not what it is (structural typing). Pick over ABCs when you don't control the implementing classes.
  • Plain annotation (x: int) — the default; use when you already know the exact concrete type.
  • dataclass/Pydantic (later days) — when you want a real object / runtime validation.
03ROADBLOCK → FIX

The classic wall: mypy --strict floods you with error: Function is missing a type annotation and Need type annotation for.... Beginners disable strict; engineers instead annotate incrementally and use reveal_type(x) to see what mypy infers, plus # type: ignore[code] sparingly on genuinely untypeable third-party calls. The fix is precision, not surrender.

04KEY IDEAS / HINTS
  • Literal["A","B"] pins a value to an exact set — kills typo bugs a bare str allows.
  • X | None (3.10+) is the modern Optional[X].
  • Hints describe intent; mypy --strict is the gate that fails loud.

Pydantic v2 + Settings

0 / 150 XP
CUTOFF TARGET
Sentinel-Lite refuses to start on a bad config — fails loud at startup, not mid-run.
01CONCEPT

Pydantic validates and coerces data at runtime — it's the bouncer at your program's front door. Engineers use it everywhere untrusted data enters: API request bodies (it's the core of FastAPI), config/settings, external feeds, LLM/tool outputs. Why so popular: you declare a model once and get parsing, validation, coercion, and clear errors for free, instead of hand-writing if not isinstance(...) checks. BaseSettings does the same for env vars/config.

02ALTERNATIVES
  • Pydantic — runtime validation at I/O boundaries (the default choice today). Pick when data is untrusted.
  • dataclasses (Day 3) — internal value objects you already trust; no validation overhead.
  • TypedDict — static-only hints for dict-shaped data; zero runtime cost, zero runtime safety.
  • attrs / marshmallow — older ecosystems; Pydantic v2 (Rust core) is faster and now the default for new work.
03ROADBLOCK → FIX

The big one migrating to v2: validators changed. People hit @validator is deprecated and confusing ValidationErrors. The fix the community reaches for: use @field_validator (v2 name) and model_config = ConfigDict(...) instead of the old class Config, and read the error's .errors() list — it tells you exactly which field and rule failed. Second gotcha: Pydantic coerces ("5" → 5) which can hide bugs; use Strict types when you want hard rejection.

04KEY IDEAS / HINTS
  • BaseSettings auto-loads from env vars / .env.
  • Fail-fast: validate everything you depend on before doing real work.
  • TypedDict vs Pydantic = static-only hint vs runtime-enforced. Use both, in their lanes (internal vs boundary).

03 ○ UPCOMING

Dataclasses, __slots__, frozen

0 / 150 XP
CUTOFF TARGET
Sentinel-Lite's internal value objects are frozen+slots dataclasses, and you can state the memory win.
01CONCEPT

Dataclasses generate the boilerplate (__init__, __repr__, __eq__) for data-holding objects. Engineers use them for internal value objects — the records, results, and configs that flow through a system. frozen=True makes them immutable (safe to share, hashable, no spooky mutation); slots=True drops the per-instance __dict__, cutting memory and speeding attribute access — which matters a lot when you hold millions of them.

02ALTERNATIVES
  • dataclass — the default for internal objects.
  • Pydantic model — when you need runtime validation (boundary). Heavier; don't use for hot internal objects.
  • NamedTuple — immutable + tuple-like + lightweight; pick when you want positional/iterable access.
  • plain dict / TypedDict — when you genuinely just need a bag of keys and don't want a type.
03ROADBLOCK → FIX

Two classic walls: (1) mutable default args — field: list = [] raises ValueError: mutable default; the fix is field: list = field(default_factory=list). (2) Wanting both frozen=True and a computed field — you can't just assign in __post_init__ on a frozen instance; the community fix is object.__setattr__(self, "name", value) inside __post_init__, or compute it as a @property.

04KEY IDEAS / HINTS
  • @dataclass(frozen=True, slots=True) = immutable + memory-tight.
  • __post_init__ validates invariants at construction.
  • The five shape tools now in hand: TypedDict (static dict) · dataclass (object) · Pydantic (validated) · NamedTuple (immutable tuple) · Protocol (interface).

OOP design: SOLID + Protocols

0 / 150 XP
CUTOFF TARGET
swappable Detector + Remediator interfaces wired into an orchestrator via constructor injection — add a 3rd detector without touching the orchestrator.
01CONCEPT

SOLID is the shared vocabulary engineers use to justify design in reviews and interviews. The two that earn their keep daily: Single Responsibility (one reason to change per class) and Dependency Inversion (depend on abstractions, inject the concretes). In Python you express the interface with Protocol. Why it matters: it's what lets a system grow — new behavior = new class, not edits to existing code (Open/Closed).

02ALTERNATIVES
  • Protocol — structural interface, no inheritance required. Default in modern Python.
  • ABC (abstractmethod) — nominal interface; pick when you want to share base implementation or force explicit subclassing.
  • Duck typing, no interface — fine for tiny scripts; doesn't scale to a team or a checker.
03ROADBLOCK → FIX

The wall: people reach for inheritance to share code and end up with fragile deep hierarchies (the classic "banana → gorilla → jungle" problem — you wanted one method, you got the world). The fix the field settled on: composition over inheritance + dependency injection — pass collaborators in, don't subclass to get them. Second gotcha: over-abstracting too early; add the interface when you have two implementations, not before.

04KEY IDEAS / HINTS
  • DI = pass collaborators via the constructor; don't new them inside.
  • Open/closed in practice: new detector = new class implementing the Protocol, zero orchestrator edits.

01CONCEPT

CPython's Global Interpreter Lock lets only one thread execute Python bytecode at a time. This is the most-asked Python systems question, and it directly governs how you scale Sentinel-Lite. (Note the 3.13+ free-threaded build is changing this — worth a sentence in interviews.)

02ALTERNATIVES
  • asyncio — high-concurrency I/O, one thread, low overhead.
  • ThreadPoolExecutor — I/O-bound work using blocking libraries.
  • ProcessPoolExecutor / multiprocessing — CPU-bound (parsing/crunching millions of rows): real parallelism, at the cost of IPC/serialization.
  • A real distributed engine (Spark — W5) — when data exceeds one machine.
03ROADBLOCK → FIX

The wall everyone hits: "I added threads to speed up my number-crunching and it got slower." Cause: GIL contention + thread overhead on CPU work. Fix: move CPU-bound work to processes (ProcessPoolExecutor), keep threads for I/O. Second gotcha: multiprocessing pickling errors / huge memory from copying data — fix by passing small inputs, chunking, or shared memory.

04KEY IDEAS / HINTS
  • Decision tree: I/O-bound + async libs → asyncio; I/O-bound + blocking libs → threads; CPU-bound → processes.
  • concurrent.futures gives one API (ThreadPoolExecutor/ProcessPoolExecutor) to swap between them.

Resilience: tenacity, circuit breaker, idempotency

0 / 150 XP
CUTOFF TARGET
Sentinel-Lite survives a flapping dependency — retries with backoff, trips a circuit breaker, and re-running a batch never double-applies.
01CONCEPT

Production systems assume dependencies fail. The standard toolkit: retry with exponential backoff + jitter (ride out transient blips), circuit breaker (stop hammering a dead dependency — fail fast, recover gracefully), and idempotency (re-processing the same input is safe). 02ALTERNATIVES

The classic failure: retry storms — everything retries in lockstep and synchronized-hammers the recovering service into staying down (the "thundering herd"). Fix: jitter (randomize backoff) + a circuit breaker + a retry budget/cap. 04KEY IDEAS / HINTS
  • Retry only transient errors; never retry a validation/4xx-type error.
  • Circuit breaker states: closed → (failures) open → (cooldown) half-open → closed.
  • Idempotency = "apply once" semantics even under at-least-once delivery.

Hashmaps & frequency

0 / 145 XP
CUTOFF TARGET
on each problem, say the trigger phrase that flags "hashmap," then state "O(n)/O(n)" before coding.
01CONCEPT

A dict gives O(1) average lookup/insert. The move: replace an O(n²) "search for a matching/related element" with one pass that remembers what it has already seen (or counts occurrences).

02ALTERNATIVES
  • Words: "have we seen," "count / frequency / how many times," "duplicate," "anagram / grouping," "pair that sums to," "first unique."
  • Constraint signal: n is large (10⁴–10⁶) so O(n²) is too slow → you need O(n).
  • Shape: "for each element, is there another element with property X?" → store what you've seen keyed by X.
03ALTERNATIVES

Hashmap when you need existence/count by key and order doesn't matter. Need sorted order → sort first (O(n log n)). Keys are a small fixed range (e.g. 26 letters) → a fixed array beats a dict. Need order and lookup → dict preserves insertion order (3.7+).

04ROADBLOCK → FIX

Reaching for a nested loop and timing out → store-as-you-go so the match is a lookup. KeyError → use dict.get(k, default), defaultdict, or Counter. Matching an element with itself → check-before-insert.

05THOUGHT PROCESS (REPEATABLE STEPS)
  1. Ask: "for each item, what related item am I looking for?" Name it (the complement, the same key, the count).
  2. Choose the key (the thing you look up) and the value (index, count, or list).
  3. One pass: check the map first (is the thing I need already here?), then add the current item. Order matters — check before insert to avoid matching yourself.
  4. State complexity: O(n) time, O(n) space.

Worked mini-example — Two Sum. "Return indices of two numbers that add to target." Trigger = "two numbers that add to" → looking for a complement. Key = the number, value = its index. Walk the array: for num, the related item is target - num; check if target - num is in the map → if yes, return both indices; then store num → index. One pass, O(n)/O(n). The naïve nested loop is O(n²) — the map removes the inner loop.

06SQL BRIDGE

Hashmap = GROUP BY + hash aggregate. Counter(items) ≈ SELECT item, COUNT(*) GROUP BY item. Building a lookup dict ≈ a hash join's build phase.

Two pointers & sliding window

0 / 145 XP
CUTOFF TARGET
on sight, classify a problem as converging-two-pointers, fast/slow, or sliding-window — and say why.
01CONCEPT

Two indices walk a sequence with O(1) extra space instead of nested loops. Sliding window is the variable-width variant: expand right to include elements, shrink left to restore a constraint — built for "longest/shortest contiguous run where X."

02ALTERNATIVES
  • Two pointers: "sorted array," "pair/triplet that sums to," "is it a palindrome," "remove duplicates in place," "max area / container."
  • Sliding window: "contiguous subarray/substring," "longest/shortest … such that," "at most K," "without repeating."
  • Fast/slow: "cycle," "find the middle," "happy number."
  • Constraint signal: the answer is a contiguous run, or the array is sorted, and n is large → O(n) needed.
03ALTERNATIVES

Two pointers (converging) → sorted, find a pair/triplet. Sliding window → contiguous run under a constraint. Fast/slow → cycle / middle. If the subarray isn't contiguous or you need all-pairs → hashmap or DP instead.

04ROADBLOCK → FIX

Off-by-one / wrong answers from mishandling when to shrink → use the fixed template (expand always; while violated, shrink; record when valid) and write the invariant as a comment. Forgetting to update the aggregate when shrinking → remove from the window exactly what you added.

05THOUGHT PROCESS (SLIDING WINDOW STEPS)
  1. Confirm it's contiguous + has a constraint you can test as you grow.
  2. Init left = 0, a window aggregate (sum / count / a Counter), and best.
  3. For each right: add nums[right] to the window.
  4. while the window violates the constraint: remove nums[left], left += 1.
  5. The window is now valid → update best. (Invariant: window is always valid after the while.)
  6. Complexity: each element enters and leaves once → O(n).

Worked mini-example — Longest Substring Without Repeating Characters. Trigger = "longest substring … without repeating" = contiguous + constraint ("no repeats"). Window = a set/Counter of chars in [left, right]. Expand right, adding the char. If it's now a duplicate, shrink from left (removing chars) until the duplicate is gone — invariant restored. Record right - left + 1 as a candidate max at each valid step. Each index moves forward only → O(n)/O(k).

06SQL BRIDGE

Sliding window = a running aggregate over a moving range (SUM(x) OVER (ORDER BY t ROWS BETWEEN ...)). Two-pointer on sorted data = a merge join.

01CONCEPT

A stack (LIFO) holds "the most recent unresolved thing" — brackets, undo, call frames. A monotonic stack keeps its contents sorted so it can answer "next greater/smaller element" in O(n). A queue/deque (FIFO) drives BFS and sliding-window-max.

02ALTERNATIVES
  • Stack: "valid parentheses / balanced," "nesting," "undo," "evaluate expression," "most recent."
  • Monotonic stack: "next greater / warmer / larger element," "days until," "previous smaller," "largest rectangle."
  • Queue/deque: "level order," "shortest steps," "sliding window maximum."
  • Constraint signal: you'd otherwise compare each element to others to its right → O(n²); monotonic stack makes it O(n).
03ALTERNATIVES

Stack → nesting/matching/"most recent." Monotonic stack → next-greater/smaller, spans. Queue/deque → BFS, window-max, producer/consumer. Need random access by index → that's an array, not a stack.

04ROADBLOCK → FIX

Not seeing the monotonic-stack case → pattern-match the phrase "next greater/smaller to the right," push indices, pop while beaten. Using a list as a queue with .pop(0) (O(n)) → use collections.deque (O(1) both ends).

05THOUGHT PROCESS (MONOTONIC STACK STEPS)
  1. Spot "for each element, find the next element to the right that is greater/smaller."
  2. Keep a stack of indices whose answers aren't resolved yet.
  3. For each new index i: while stack non-empty and nums[i] beats nums[stack[-1]] → pop, and i is that popped index's answer.
  4. Push i. Anything left on the stack at the end has no answer (default 0/-1).
  5. Each index pushed/popped once → O(n).

Worked mini-example — Daily Temperatures. "For each day, how many days until a warmer one?" Trigger = "next warmer to the right." Looks like nested loops (O(n²)) but is monotonic-stack. Stack holds indices of days awaiting a warmer day. For day i: while the current temp > temp at stack[-1], pop index j and set answer[j] = i - j. Push i. O(n)/O(n).

01CONCEPT

02ALTERNATIVES
  • Plain: "sorted array," "find target / position," "rotated sorted."

05THOUGHT PROCESS (SEARCH-THE-ANSWER STEPS)
  1. Define feasible(x) returning True/False, and confirm it's monotonic (False…False, True…True).
  2. Set lo/hi to the value range bounds.
  3. while lo < hi: mid = (lo + hi)//2; if feasible(mid): hi = mid else: lo = mid + 1.
  4. lo is the boundary — the smallest feasible value.
  5. Complexity: O(log(range) × cost of feasible).
